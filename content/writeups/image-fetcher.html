An image URL.
A file on the other side.

How an image-to-Base64 feature became full-read SSRF, then arbitrary local file read—and why a keyword filter did not close the gap.

Raahil Muhammad WildanUAT / whitehat environmentVendor-reported fix

Inside the investigation

The featureAttack chainThe file boundaryThe filter gapImpact & limitsDisclosureRemediation

The feature was supposed to fetch a picture and return its Base64 representation. The useful question was what else its URL loader would accept.

I tested POST /api/v1/image-base-64 on an in-scope UAT target, using the test credentials supplied by the program. The image parameter controlled what the backend fetched. A request to an external HTTP service came back through the API. Changing the scheme to file:// made that same feature read from the application server’s filesystem.

First, establish the server-side fetch.

I sent an HTTP URL to a service that reports the origin of a request. After decoding data.image, the response contained an origin address for the server-side request. This established that I could receive the fetched response body, rather than only trigger an outbound connection.

The address is redacted in this writeup. It was evidence of the request path, not a reason to test unrelated hosts.

Then, cross the file boundary.

The same parameter accepted file:///etc/hostname. The returned Base64 decoded to a hostname associated with the UAT environment. Reading /etc/os-release provided another system-identification check.

The trust boundary had changed: input intended to identify a remote picture could select a file available to the backend process. Those bytes were then delivered through the normal image response.

The data:image/png prefix did not establish that the content was an image. It was a wrapper around bytes the server had fetched. Base64 encoding preserved those bytes.

Why the filter did not close the gap.

A direct request for a blocked path returned 403. Variants of that path returned 200, and the original report records that the decoded content contained the expected account-file entries.

Filter’s view/etc/./passwd
Resolved path/etc/passwd

The report also records a repeated-slash variant and a double-encoded character variant. These results are consistent with the filter and the fetcher interpreting different forms of the same input. Without server-side instrumentation, the exact decoding order remains an inference.

A keyword rule could reject one spelling while leaving the URL loader’s file access available. The application needed to constrain what the loader was allowed to fetch.

The demonstrated impact is limited to the UAT/whitehat environment covered by the report. The reproduction used program-provided Basic authentication. The report submitted the issue as High severity.

Disclosure and response.

The original report describes manual testing against the in-scope environment. It states that no customer data was accessed and no destructive actions were performed.

In the supplied response, the security team said the issue had been resolved and asked me to retest. The message also described reward processing after confirmation and a planned Hall of Fame acknowledgment.

That response documents the vendor’s stated fix. It does not establish a completed retest, a paid reward, or a published Hall of Fame entry. Those outcomes are not claimed here.

Close the boundary at the fetcher.

  • Allow only intended sources. Parse the URL on the server, require HTTP(S), and allow only approved image hosts. Reject unsupported schemes before any fetch.
  • Validate the destination that will be used. Canonicalize once with a trusted parser. Check resolved addresses and prevent access to loopback, private, link-local, and metadata destinations.
  • Recheck every redirect. Apply the same scheme, host, and resolved-address rules to each destination, or disable redirects.
  • Constrain the fetch and response. Use timeouts and size limits. Check that the returned bytes are a supported image before processing or returning them.
  • Reduce the consequences of a missed check. Restrict network egress and the files available to the application process. Keep sensitive configuration outside its readable paths where possible.

WAF rules can support these controls. The decisive fix is ensuring that a feature built for images can access only the resources it needs.
