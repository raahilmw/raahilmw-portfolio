How an image fetcher let me read server files.

I started with an image URL and found a way to read files from the application's UAT server.

Raahil Muhammad WildanSSRF / file read

The security team accepted the finding and confirmed that they had fixed it. Their reply also explained the reward process and asked me to retest.

The images are privacy-edited renditions of my captures. Request details below follow my original report.

What I was testing

I was testing an image-to-Base64 endpoint in the program's UAT environment, a server used for testing. I accessed it with the Basic Auth credentials supplied by the program.

The endpoint, POST /api/v1/image-base-64, accepted an image parameter containing a URL. It fetched that resource and returned its contents in data.image.

That made the URL an interesting place to test. Could I control what the server fetched, and would it send the result back to me?

Confirming a server-side request

I first supplied an HTTP URL for a service that reports where a request came from. The endpoint returned a Base64 response. After decoding it, I could see an origin address for the server-side request.

This confirmed server-side request forgery (SSRF): I could make the backend fetch a URL I chose. I could also read the fetched response through the API.

Changing the URL to a local file

Next, I replaced the HTTP URL with file:///etc/hostname. The file:// scheme refers to a file on the machine handling the request.

The endpoint accepted it. Decoding the returned data gave me the UAT server's hostname. I also read /etc/os-release to confirm the behavior with another system-identification file.

The response still used a data:image/png;base64 prefix. That label did not mean the bytes were a PNG. Base64 is an encoding, so decoding it recovered the file contents.

Working around the path filter

A direct request for /etc/passwd returned 403 Forbidden. I then tried different spellings of the path, including a dot segment, a repeated slash, and an encoded character.

Those variants returned 200 OK. During testing, I decoded account-file entries from the response. The encoded request below was one of the successful variants.

I also tested file:///proc/./version. The screenshot shows another successful request using a dot segment.

The results showed that the filter did not consistently block paths that the file loader could resolve. I did not have server-side instrumentation, so I could not determine the exact decoding order.

The path variants in the report
file:///etc/./passwd
file:///etc//passwd
file:///etc/pass%2577d

These are the recorded inputs. The target and authentication values are omitted.

How far I went

The confirmed impact was arbitrary local file read through the image endpoint, limited to files the application process could access.

A database-configuration path also returned a non-empty response. I stopped before decoding it because it could contain credentials. I did not verify usable database credentials or test database access.

The report covered the UAT environment. I did not access customer data or perform destructive actions. I submitted the issue as High severity, with the program-provided authentication described in the report.

What needed to change

The application needed to restrict the resources its image fetcher could access. The recommendations in my report were to:

  • Accept only HTTP(S) URLs from approved image sources and reject other schemes.
  • Validate the parsed destination and resolved IP address, including each redirect. Block private, loopback, link-local, and cloud metadata destinations.
  • Check the returned bytes as an image, with limits on response size and fetch time.
  • Restrict the network destinations and local files available to the application process.

The WAF blocked some direct requests, but alternate path forms still reached the file loader. Application-level validation had to enforce the restriction consistently.

The security team's email above records their confirmation of a fix and request for retesting.
